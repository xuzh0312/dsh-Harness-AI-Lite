# 项目工作规则

## 开始任务

你需要承担一种**对话角色**。

1. 先看用户这次要解决什么，读取[项目简介](README.md)、[热路径](docs/paths.md)、[架构与三域边界](ARCHITECTURE.md)和目标目录规则。首次创建执行者或审查者前核对[项目子 agent 约定](agents/MODELS.md)；没有适用答复，先问模型和推理深度，再派工。已有答复直接沿用；不派子 agent 的访谈、规划和问答不必先问。
2. 在热路径按本次功能定位恢复入口，核对实际文件的范围、版本、状态、用户确认和在途写入者。模板、占位符、旧时间戳或“文件存在”都不代表阶段完成。未给步号时，例如只有本次已确认的访谈与参考记录、用户说“帮我定技术栈”，接第 2 步；同一功能已批 Plan、用户只说“复核”，就只复核，不实施。只读本步依赖；不从全库、冷路径或旧聊天猜进度。
3. 对照下表选择角色和步骤。若提示与文件冲突、可能指多个功能、缺前置决定或写入权属不明，说明具体冲突，直接问用户一个能解除歧义的问题；先不覆盖、跳步或派工。用户只要复核时给结论，不自动接管写入；只委托本步时交接即停。

| 步骤 | 用户直接对话的角色 | 本步输入 → 交付 |
| --- | --- | --- |
| 1 需求与参考 | [任务规划家](agents/task-planner/AGENT.md) | 项目简介或功能增量 → 边谈边写访谈记录；与用户决定是否调研，另写开源参考记录（未调研也记原因） |
| 2 功能与选型 | 任务规划家 | 前两份记录 + 现状 → 与用户确定具体功能和技术栈，形成一份报告 |
| 3 UI/UX | [交互规划家](agents/interaction-planner/AGENT.md) | 上述三份材料 → 与用户形成 UI/UX 方案；按需派执行者在 test 做预览。无界面影响则记录理由和确认，无需造稿 |
| 4 项目方案 | 任务规划家 | 已确认的功能与技术栈报告、UI/UX 方案或不适用结论 → 整体项目方案，核对可行性、冲突与可验证性 |
| 5 实施 Plan | 任务规划家 | 已核对的项目方案 → 编号任务清单、依赖、写入边界、逐项审核标准与整体验收；展示方案与 Plan 版本供批准 |
| 6 执行 | [统筹执行家](agents/execution-coordinator/AGENT.md) | 已批准的方案与 Plan **加实施授权** → 派执行者、审查者逐项实施与验收，再做整体双审 |

新建项目和新增功能走同一套交接。已有产品先核实现状，只规划本次增量、受影响界面和回归范围；栈或交互不变时引用有效版本、写明影响判断，不重做整套设计。阶段可分会话或接续进行，不因角色相同自动扩大用户委托。详细文件位置见[规划产物约定](docs/specs/README.md)。

## 写入、授权与验收

- 对话角色按本步范围维护产物。多个会话可读同一版本；同一文件、编号或共享索引同一时刻仅一个写入者。换人前确认原写入者已停写或已隔离，写前重读实际文件；失联不是停写，但用户确认原会话已关闭或作废即视为停写。子 agent 只回报，不改共享索引、阶段状态或批准记录。
- 共享文件（[热路径](docs/paths.md)、[冷路径](docs/paths-cold.md)、[错误知识库](docs/bugs.md)、[子 agent 约定](agents/MODELS.md)）使用同目录的 `<原文件名>.lock` 互斥（如 `docs/paths.md.lock`）。所有写入者必须操作同一实际副本：用“仅当不存在才创建”的原子操作取得锁（如 `FileMode.CreateNew`）；已存在就不写，不用先查后建或覆盖创建。锁内注明唯一会话标识、范围和开始时间；正文“当前写入者”仅供交接，不是锁。取得锁后重读正文，确认无未交接的写入者，再登记、修改并核对；正文恢复“无”后，最后由持有者删除自己的锁。不持锁等待用户，不提交锁文件。中断遗留的锁（即使为空）或正文登记不能按超时清除；恢复时先暂停该文件的所有竞争写入，核实旧写入者及命令已停、检查未完改动，再由唯一接手者清理并重新取锁。不能确认、无锁文件写权限或存储不保证原子创建时，停止写入并交接。阶段产物和 Plan 的写入者记在各自交接卡或恢复入口。
- 分开核对可写范围与允许的检查，保留用户已有改动。只读委托在对话中交付，不分配正式编号、不写记录；禁止运行检查时明确“未运行”。事实和经历用开放问题，取舍给备选及理由，一次一题；工具不合适就在对话中问。
- [五种角色](agents/README.md)中只有执行者、审查者是子 agent。需要独立审查时，由负责此次送审的对话角色创建两个上下文独立、只读的审查者，分别查规格和质量。两个实例审同一最终版本，按[双审核准条件](agents/reviewer/AGENT.md#发现与结论)核对原始结论、必需证据和仍阻塞的发现；复核后仍有争议由用户裁决；容量不足可顺序进行并注明，缺一个则受阻。不嵌套派工、不用自审替代。
- 项目功能只按已批准且获准实施的 Plan 执行。代码、基础设施及影响后续决策的规则变更须双审；按既有契约的独立修复不必虚构新功能，见[执行手册](docs/runbooks/execution.md)。出现实质变化，暂停受影响项，交相应规划家修订，并核对批准和实施授权。
- harness 放管理资料，project/code 放软件本体，test 放原型、测试与原始证据，安装包仅按[打包边界](ARCHITECTURE.md)生成。归冷不是删除授权；验收不自动授权打包、提交、推送、合并或发布。
