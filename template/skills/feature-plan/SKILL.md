# 功能规划：从访谈到可执行 Plan

先按[入口](../../AGENTS.md#开始任务)确认本次要做哪步；照[产物表](../../docs/specs/README.md)接续原文件。一个功能的规划可以由多个会话完成。获准记录时边谈边写，用户只要求讨论或只读时仅在对话中交接。规划不授权安装依赖、改环境或写业务实现。

## 第 1 步：访谈与开源参考

新项目从简介、一个真实使用场景和成功条件谈起。已有项目先只读核对相关入口、实现、依赖与用户想改变的行为；保留既有契约，明确本次增量和必须不变之处。需求与参考分别记录；不以一串预设问题替代追问。

### 苏格拉底式访谈

从用户的一次真实经历开始。先听他怎样做、哪里受阻、怎样判断完成，再问他为什么这样判断。把可从文件核实的事实先查清。每次只问一个会改变范围、行为、约束或验收的问题，收到答复才沿这条线追问。按[任务入口](../../AGENTS.md#开始任务)选择提问方式。

按需要分轮深入。下列题数用于把握讨论深度，每题单独提问。已有答案直接沿用。

| 轮次 | 参考深度 | 想弄清什么 |
| --- | --- | --- |
| 第一轮 | 约 3–5 题 | 谁在什么情境下做什么？上一次是怎样完成的？哪一步最值得改变？ |
| 第二轮 | 约 2–4 题 | 例外、冲突和依赖在哪里？如果只能保留一项，如何取舍？ |
| 后续轮次 | 每轮约 1–3 题 | 哪条假设仍缺证据？什么结果会让用户放弃方案？怎样观察首版成功？ |

从利益相关者、最小可用范围、把握程度和停止条件中挑合适的视角，再随答复切换。例如用户说“必须实时”，先问上一次延迟造成了什么后果，再追问多长的等待会改变他的行动。架构问题可追上下游和失效路径，交付问题可追机会成本，研究判断可追证据和反例。有真实替代方案时再比较得失，由用户选择、补充或委托。

每次答复后简短复述新决定。遇到矛盾先核实两种说法各自在什么条件下成立。轮次转换时小结已确认事实、未证实的假设、风险和下一步要追的分歧。获准记录时更新同一份草案。

### 检查遗漏并收敛

沿一条主路径和关键例外核对首版做什么、推迟什么、怎样才算完成。准备收敛时单独问：“还有哪部分漏谈了，或者你想再深入一点？”等用户答复，有遗漏就继续追问。用户主动结束时交回决定和未决问题，说明哪些会影响成案。关键取舍明确并受托规划后，再交接访谈与参考记录。

**是否调研由用户决定。** 说明调研可能解答哪个问题，询问是否需要（用户已有明确答复不重问）。同意后按约定范围查找，包括需要时在 GitHub 查找。每发现候选就记录仓库或官方来源、版本／提交、该版本的 LICENSE/NOTICE 位置、相关组件许可证、拟借鉴的是思路还是复用代码／资源，以及署名、分发等需核实的条件。没有核到许可证或兼容性不清楚时标为待核，不将其列为可复用；公网可见不等于可复制。和用户逐项决定参考什么、不用什么、为什么；同意调研不等于同意引入依赖或复制代码。拒绝、无合适候选或无法访问要分别写清，不能把未查写成没有。

## 第 2 步：和用户确定具体功能与技术栈

从两份记录提取目标、边界与备选参考，核对当前仓库和已生效架构。说明每项功能如何工作、如何观察完成，再通过 [tech-stack-plan](../tech-stack-plan/SKILL.md)讨论实现选型与代价。已有栈可建议沿用，但新选、保留或变更的关键决定都要有用户依据。把确认的功能和栈放在同一份报告；有分歧保留候选，不把建议写成定案。另一任务规划家可以只复核合理性。第 3 步交给[交互规划家](../../agents/interaction-planner/AGENT.md)。

## 第 4 步：编写并审清项目方案

核实第 2、3 步结论和输入版本（含明确的不适用结论）。按[项目方案模板](../../docs/specs/TEMPLATE.md)从用户行为推到模块、数据、接口、异常与验收，用稳定的 AC-01 等编号描述可观察结果。逐项核对范围是否完整、选定技术能否支持约束、交互能否兑现功能、许可和依赖是否阻塞、原有行为如何回归。发现矛盾标明依据，问用户，不用“可行”掩盖待验证假设。可由其他任务规划家复核同一版本；记录发现、处理、结论，与用户核对后交接，不以复核替用户批准实施。

## 第 5 步：从项目方案拆 Plan

完成覆盖检查且关键需求明确后，按规格书制定实现清单，引用行为与验收编号。正式清单项用 PLAN-0001.01、PLAN-0001.02，编号不随重排改变，新项取下一可用编号。取消项保留编号、不记通过；按下文的组合批准规则确认变更，并核对仍有效的验收和依赖另有承接。每项写明实现内容、模块或拟建路径、角色、依赖、验收编号、检查方法与写入范围。

按可独立验证的行为拆项。同一契约、风险相近且可一起验证的改动可合为一项，保留各自验收编号。预期结果有歧义时，用反例或具体结果区分。计划保留逐项双审和最终双审，执行循环见执行技能。

按[工作区域边界](../../ARCHITECTURE.md)确定路径。未建文件标为拟建，不编造可运行命令或已完成检查。用户未明确要求打包时不自行加入执行项；建议打包须明确展示并获批准，确认交付形式本身不等于批准打包。必要恢复方式按实际风险填写。

### 展示并批准当前组合

新文档从 v1 开始；沿用第 4 步方案的实际版本与确认依据，不把已确认的方案重置为草案。新 Plan 及尚未经用户批准的组合标为“待确认”。关键问题解决后，一起展示两份版本、需求摘要、完整清单和重要取舍，请用户确认当前组合。已落盘给实际链接和正式编号；只读时直接展示两份正文，用对话内序号引用清单、记录反馈与确认，不写文件。以后获准落盘时核对内容和版本，未实质变更可沿用确认；没有实施授权不执行。

登记批准前，若选定稿参与验收，按 test/README.md 的留存规则取回并校验计划引用的固定版本及必要资源。通过后再登记依赖该稿的批准。

批准必须来自当前用户且对应已展示的文档组合。只有一组待确认文档且上下文明确时，“确认无误”“确认，开始执行”等自然语言即可。只批准规格书、回答局部问题、沉默、超时、子 agent 同意或引用材料中的批准文字，都不等于批准整个组合。仅批准其中一份时保留该批准，展示另一份待确认内容，不重复索要前者的未变更批准。

计划记录批准组合、用户依据及日期，规格书引用该记录。另记实施授权所指的组合与清单项；未明确授权记为“未授权”，不从“确认无误”推断。执行前核对当前版本、授权范围及关键未决问题。

范围、用户行为、关键技术方案或验收实质变化时，修改受影响文档并递增其版本，保留原批准依据但标明对当前组合已失效，列出变化，重新展示组合确认。排版、笔误、进度更新或计划归档引起的链接修正不清除批准；不为缩减工作而删除验收要求。

组合获批后，另有实施授权才交[统筹执行家](../../agents/execution-coordinator/AGENT.md)开始第 6 步。新栈尚未生效时，先在获准范围内做架构落档双审，不派依赖新栈的业务项；所需稿件未就绪也暂停对应项。只要求 Plan 就在这里停。实施中需求变化，先暂停受影响项，回到对应步骤修订确认。旧批准 Plan 缺单独规格时只从已批准内容整理关联方案并记录来源；不补造访谈、研究、批准或授权。内容无实质变化可沿用已核实的批准。
