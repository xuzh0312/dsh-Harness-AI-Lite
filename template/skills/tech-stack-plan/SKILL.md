# Tech Stack Plan：技术栈与项目架构约束规划

技术栈未定且用户希望共同选型时，从场景访谈开始。已有明确选型（含用户直接指定换栈）时，直接进入[选型与交接](#选型与交接)。沿用已核实的事实和用户答复。

## 从场景查明约束

先查资料，再问会改变选型的问题。下表用于发现遗漏，不是访谈清单。可以追问真实经历、用反例区分两种解释，或直接提出有依据的方案。按[开始任务](../../AGENTS.md#开始任务)逐题追问使用场景、约束和依据。遇到真实的技术取舍再比较选项和推荐理由，沿用已有答复。

| 方面 | 可以怎么问 | 回答会影响什么 |
|---|---|---|
| **1. 用户与核心流程** | “请选一位典型用户，从他打开软件开始，讲到他完成一次任务。”“第一版必须把哪条流程跑通？” | 确定主要交互方式，以及界面、计算、存储各自承担什么工作。 |
| **2. 运行环境与部署** | “软件具体在哪台设备上用，谁来安装？”“断网时，哪一步仍要能完成？”“能申请管理员权限吗？” | 判断网页、桌面端、移动端各自是否可行，是否需要本地运行或独立部署。 |
| **3. 数据与协作** | “数据从哪里来，最后要到哪里去？”“两个人会同时改同一条记录吗？”“换电脑后，哪些数据必须跟过去？” | 决定文件、本地数据库或服务端数据库是否合适，以及是否需要同步和冲突处理。 |
| **4. 规模与性能** | “拿一次最重的任务举例，一次要处理多少数据？”“用户能接受等多久？等待时还要继续做什么？” | 判断是否需要后台任务、流式处理、并行计算或硬件加速，也能得到可测量的验收条件。 |
| **5. 外部依赖与兼容** | “必须对接哪些设备、文件格式、接口或现有系统？”“有没有一个真实样例，或者已经能运行的 SDK 示例？” | 识别会直接限制操作系统、语言、运行时或库版本的依赖。 |
| **6. 安全、可靠性与恢复** | “哪些数据可以离开设备，谁有权查看或修改？”“如果保存时断电，最多能接受丢掉多少工作？恢复由谁操作？” | 明确权限、存储边界、事务、备份和恢复要求。 |
| **7. 交付与长期维护** | “第一版什么时候要交给谁使用？”“半年后谁来修问题、发更新？他熟悉什么技术？”“时间紧时，哪项可以推迟？” | 在可行方案中权衡学习成本、打包更新、运维负担和交付速度。 |

例如，“只有我自己用”不能排除换机续接；问清手动迁移是否可接受，再决定是否需要同步服务。

## 选型与交接

说明选什么、由哪条约束决定、仍需验证什么；有实质不同的方案时再比较。已委托的细节给出建议与理由。请用户确认关键选型，已有确认直接沿用；要求提前结束时列出未决事项，不替用户定案。

第 2 步由任务规划家将选定功能、栈、备选依据和用户确认写入[具体功能与技术栈报告](../../docs/specs/README.md)；只读则在回复中交付。已有项目先核实现有栈、受影响的模块和兼容要求，无需换栈就注明沿用。**报告确认不等于改变生效架构**；后续可以按已确认的候选设计和拆 Plan，不能提前安装或实现。本步无需为了审批候选栈提前创建 Plan。

首次落档或换栈时，将生效作为第 6 步首个依赖新栈的实现项之前的前置工作；用户若明确要求提前启用，则单独交统筹执行家办理。取得选型确认和相应写入授权后，统筹执行家在已有 Plan 或独立 TASK 中保存 [ARCHITECTURE.md](../../ARCHITECTURE.md) 的完整候选差异（含生效依据）、原生效版本与候选版本。送审期间原栈不变，首次则仍为未定。审查者规格实例核对用户确认，质量实例核对可行性与兼容性。同一候选满足[双审核准条件](../../agents/reviewer/AGENT.md#发现与结论)后，核对基线、原样应用差异、核验落盘并记录生效；依赖新栈的实现到此才能开始。候选或基线实质变化重新送审。

若落盘中断，接手者核对原版、实际文件、候选、两份报告与授权；完全匹配才补做核验。退回、取消或核验失败，记录上次生效栈和实际差异，不把候选写成已生效，也不擅自回滚用户改动。
