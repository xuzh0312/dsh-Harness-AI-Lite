# Bug Detect：项目错误知识库

用于 reviewer 检查错误、检索历史解决方案及复验修复。知识库为当前 Harness 的 [docs/bugs.md](../../docs/bugs.md)，跨项目不混用。它保存可复用的问题和已验证方案，不保存逐轮审查流水。

## 调用与权限

负责送审的对话角色显式读取本技能并将路径传给 reviewer；reviewer 发现错误或复验修复时必须读取并执行。

reviewer 对代码和知识库保持只读，调用技能后返回查询结果及记录提议。只有负责送审的对话角色串行写入知识库；写前重读最新内容、重新去重并分配编号。多个 reviewer 不直接写文件。implementer 修复前读取匹配条目，已有方案仍须验证是否适用。

## 查询、确认与去重

1. 核实具体触发条件和可观察后果。静态推理可作为证据，但必须给出完整路径，标明未运行；审美偏好、推测性问题、无关建议不进入知识库。尚无法确认缺陷的疑点先留在审查报告。
2. 已有 BUG 编号先查原条目；没有匹配时用症状、模块、错误码和根因关键词搜索当前项目知识库，只读候选条目。没有记录时返回未命中，不从其他项目导入错误。缺陷已确认但根因未知时，可新建待定位条目并注明“根因未确认”。
3. 根因、触发机制及修复原则一致，且不存在已知不同的适用约束时，复用原 ID。文件、页面或报错文字不同不单独新建。只有报错相似但根因不同，或无法确认属于同类时，不强行合并；明确不同则新增，不确定则先定位或保留待定位记录。
4. 同一问题的同轮反馈、重复扫描和重复证据不新增、不增加次数。已解决问题在新的已确认发生场景复发时，更新原条目、复发次数和最近发生信息；无信息增量则不写文件。
5. 根因确认后发现两个条目实为同类，负责送审的对话角色合并到较早 ID，汇总仍有效的信息、修正项目内引用，保留旧 ID 为别名且不再复用。不同根因不能为压缩日志而合并。

## 状态与方案证据

| 状态 | 条件与操作 |
| --- | --- |
| 待定位 | 缺陷及影响已确认，根因仍未确认；不能写成已知根因 |
| 待修复 | 根因及修复方向已明确，尚未完成实现 |
| 待验证 | 已有实现，但缺少原问题的行为验证或 reviewer 复核 |
| 已解决 | 相关问题范围的修复验证通过，reviewer 复核通过，负责送审的对话角色核对证据后关闭 |
| 已撤销 | 已记录的发现被证据证明为误报；简记原因，撤掉错误方案，避免后续误用 |

同类错误复发时从已解决重新进入对应未解决状态，保留历史有效方案及适用范围，明确本次复发尚未解决。复发次数只对新的、已确认的发生场景累计一次，不按审查轮次计数。

“建议方案”和“已验证解决方案”必须分开。执行者声称修好、编译通过或无关测试通过，不能单独把状态改为已解决。复核需覆盖原始触发行为及相关回归；若用静态方式验证，说明它为何足以证明该问题已经消除及覆盖限制。涉及当前复发的缺口不得被旧的成功验证掩盖。

## 返回送审者的记录提议

除正常审查结论外，每个有效缺陷返回以下内容：

- 操作：新增／更新／重新打开／合并／无需变更；候选 ID 或未命中及去重理由。
- 定位关键词、症状、触发条件与影响、根因及确认依据；新旧场景的适用差异。
- 建议状态；建议方案与已验证方案分别注明。
- 证据：任务或发现引用、代码版本或未提交范围、复现及验证方法与结果；未验证项。

reviewer 不预先占用新 ID。只读任务仅在对话返回提议，不写库或分配编号；允许写入时由持有本次知识库写入交接的对话角色登记并返回最终 ID。编号使用 BUG-0001 形式，扫描既有编号（含合并别名）取最大值加一，不重用旧编号。

## 单条记录格式与压缩

负责送审的对话角色在知识库追加或更新一个章节，不为每次发生创建文件：

```markdown
## BUG-0001：简短问题标题

- 状态：待定位／待修复／待验证／已解决／已撤销
- 检索关键词：模块、症状、根因关键词
- 触发条件与影响：最小必要描述
- 根因与依据：已确认原因；未确认则注明
- 建议方案：尚未验证的候选处理；无则注明
- 已验证解决方案与适用范围：无则注明；保留重要约束或反例
- 验证证据：方法、实际结果、代码版本或工作树范围、reviewer 复核结论
- 首次发现／最近发生：日期与任务或发现引用
- 复发次数：0（首次发现不算复发）
```

仅保留可复用的方案、必要限制及能复查的证据引用。多次相同错误更新最近发生信息，不追加逐次时间线；重要的新适用条件或失败方案可简记其原因。原始日志、复现脚本、测试代码及验证产物均存放 test，harness 只引用必要证据，不复制完整日志或敏感数据。合并别名仅在实际合并时添加。
