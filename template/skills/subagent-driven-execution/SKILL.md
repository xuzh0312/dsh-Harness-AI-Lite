# Subagent Driven Execution：逐项派工与独立验收

统筹执行家读取当前规格书、计划和 [执行手册](../../docs/runbooks/execution.md)，按“单项实现 → 两个并行 reviewer 独立审查 → 返工复验 → 统筹执行家验收”循环执行，最后由新的两个 reviewer 完成整体审查。本技能借鉴 Superpowers 的任务驱动方式，使用当前运行器的子 agent 工具，无外部插件、后台调度器或 Bash 脚本依赖。

## 1. 核对批准与恢复位置

确认用户授权实施，当前规格版本和计划版本与批准组合一致，关键问题已解决，路径、权限、依赖和当前代码状态已核实。仅要求规划时不启动；实质变化回到 [feature-plan](../feature-plan/SKILL.md) 修订确认。依赖选定稿的实现项，首次派工或恢复时按 test/README.md 取回计划引用的版本并校验稿件及必要资源。核验失败时暂停该项，恢复原版或由用户确认可独立验收的文字依据后继续。不因换会话重复索要仍有效的批准。

每次派工、恢复或返工前，从热入口和当前项目方案核对本项依赖的功能与栈、UI/UX 等上游产物的实际版本与状态，不能只比对 Plan 与方案两个版号。旧批准记录即使尚未改写，只要依赖已换版、标为需复核、无法核对或与用户提示冲突，暂停受影响项，核实影响；有歧义就问用户。实质变化须修订并确认相应组合与授权；无关项的有效批准不撤销，不读取不相关的冷档。

使用原计划作为唯一进度记录，按[计划模板](../../docs/plans/TEMPLATE.md)保存当前项、执行者身份、基线、简报、交付与审查摘要、返工轮数、证据和下一步。启动或恢复时核实真实文件、在途状态和证据，不重复派工。原执行者不可恢复时，先确认停写或隔离其写入范围，再把已验证交付和未完成项交给新实例；状态不明时不补派重叠写入。

旧已批准计划缺独立规格书时，先按 feature-plan 的兼容规则整理关联规格；不借补文档增加未经批准的需求。

## 2. 为一个实现项准备简报

首次派工前对照跨项接口的提供方与使用方，核对字段、单位及失败约定。按计划顺序选择已授权且依赖满足的一项；上一项独立审查并验收后再开始下一项。必要只读调查可并行。

每个新实现项创建新的 implementer 上下文。子 agent 不嵌套创建 agent；reviewer 由统筹执行家派出，执行者自审不替代独立审查。

按[交接模板](../../agents/TASK_TEMPLATE.md)引用原计划当前项及相关 AC，不复制聊天、整份计划或已完成项。界面项说明关键状态、交互约束和待实测场景；有稿给位置，无稿引用获批规格或既有界面，不为派工补稿。

统筹执行家派工前记录相关仓库提交和已有未提交改动边界；未提交内容、未跟踪文件或无 Git 的区域，需要时在 test 保存相关文件的前置快照，供完整内容比对。不能只靠事后 git status 或 HEAD~1 推断本项差异，也不为方便审查擅自提交或初始化仓库。

创建实例遵守 [MODELS.md](../../agents/MODELS.md)。

## 3. 接收实现与验证报告

执行者在分配范围内实现、验证并自审，按[角色协议](../../agents/README.md)回报。统筹执行家不在执行者工作期间改其文件，也不接管实现以绕过审查；需调整时先更新分派边界。

统筹执行家核对实际交付和证据，有缺口先补材料、返工或说明阻塞。按[路径表](../../docs/paths.md)在下一次派工或送审前更新稳定索引；无写权限时交接实际路径与待同步项。

按[工作区域与打包规则](../../ARCHITECTURE.md)存放文件。当前授权未覆盖打包时不生成安装包；不额外提交、推送、合并或发布。

## 4. 派出两个并行 reviewer

每项交付后，按 [reviewer 协议](../../agents/reviewer/AGENT.md)创建 reviewer-spec 与 reviewer-quality，独立并行审查。两者拿到同一简报、基线、完整差异、执行报告和证据；包括已提交和未提交变化，无 Git 时比对前置快照。原始材料放 test，计划只记位置和覆盖范围。

冻结受审版本，分别保留两个实例的结论。统筹执行家按[双审核准条件](../../agents/reviewer/AGENT.md#发现与结论)核对同版本报告、必需证据、裁决及剩余阻塞，再决定能否验收。容量不足时两实例顺序审查并注明；缺任一实例则受阻。

发现缺陷或复验时，reviewer 调用 [bug-detect](../bug-detect/SKILL.md)，只返回去重后的记录提议，统筹执行家串行写项目错误知识库。子 agent 不直接改共享记录。

## 5. 返工、逐项通过与中断恢复

统筹执行家核实每项发现，记录接受修复的决定；有证据认为不成立时，先请原 reviewer 复核，仍不一致按[结论冲突与用户裁决](../../agents/reviewer/AGENT.md#结论冲突与用户裁决)交用户决定，不自行拒绝。返工优先恢复原执行者，提供具体发现、验收与允许范围；无法恢复或需要换参时，把已证实、已排除及待查的事项交给新实例。

修复后重跑受影响检查，两位 reviewer 都能查看基线至同一最终版本的完整差异，重点复核本轮变更、原发现和相关回归；未受影响的证据可复用，但两个实例都要确认当前版本。优先恢复原实例，无法恢复或需要换参时交接。两份结论符合通过条件后，统筹执行家再核对证据。连续两轮同一问题且无新证据，按执行手册重查，不机械重试，也不把未满足的验收挂起后算完成。

统筹执行家仅在本项符合规格、质量及必要检查均满足后勾选通过。保存差异范围、实例身份、两份结论、证据和下一步，再释放无需继续工作的实例。剩余项未获授权时保留原计划，等待授权。

计划中纯审查条目直接由两个 reviewer 分工完成，统筹执行家验收条目由统筹执行家执行，不给 reviewer 的报告再递归安排审查。真正修改实现后仍须由两个实例复验并满足同版本通过条件。

缺少权限、依赖、运行器能力或必要决策时记录具体阻塞、已尝试动作、影响及恢复条件；不开始依赖该条件的实现。其他独立且已授权的只读调查、文档准备可以继续。恢复时重新核实受影响证据，保留仍有效的批准与已验收项。

## 6. 整体审查与最终验收

当前批准范围的实现项均通过后，统筹执行家新建 reviewer-spec 和 reviewer-quality，并行审查当前完整规格和功能开始以来的完整差异。前者检查验收覆盖与跨项行为，后者检查接口、数据流、回归及最终证据。取消项保留历史，不能漏掉仍有效的验收或依赖；整体审查仍须满足第 4 节的同版本双审条件。

整体发现仍按修复、验证、独立复验处理；仅重开受影响项。若仍有未获实施授权的待办项，记录本批结论，Plan 保留 active；不把本批通过当作整个 Plan 完成。仅在整个 Plan 的必需检查和最终验收满足后，更新规格状态与计划证据，将计划归档 completed，修正规格链接，最后核对路径索引。

最终回复说明完成内容、实际验证及限制。未完成、受阻、未运行的必需检查不能标为通过，验收完成不自动授权额外的 Git 操作或发布。
