# 规划产物与跨会话交接

一次规划对应一个项目首版或一个功能增量，不为不同会话复制整套材料。以下都是 **harness 相对路径的命名约定**，仅在实际副本、对应阶段获准写入时创建。`<ID>` 代表 `PLAN-` 加四位编号；第 1 步用它关联材料，并不表示已有 Plan 或已获实施授权。编号预约、重用与归档见[编号规则](../plans/README.md)。

| 步骤 | 文件 | 最少要写清的内容／何时可交接 |
| --- | --- | --- |
| 1 | `docs/specs/<ID>/interview.md` 访谈记录 | 谁在什么场景做什么、问题和反例、首版边界和非目标、用户原意、已定与未定；每个影响方案的答复就地更新，和用户核对小结 |
| 1 | `docs/specs/<ID>/references.md` 开源参考记录 | 调研决定和范围；逐项记录来源、固定版本、许可证依据、拟参考部分、义务或疑点、与用户讨论后的采用／排除／待定结论。跳过或没有合适候选也记录原因，不伪造结果 |
| 2 | `docs/specs/<ID>/features-stack.md` 具体功能与技术栈报告 | 每项功能的用户、入口、输入输出、边界、异常和成功条件；现有栈、备选及取舍、沿用／新增／替换、迁移和兼容影响、用户确认。区分报告结论与已生效架构 |
| 3 | `docs/specs/<ID>/uiux.md` UI/UX 方案 | 根据前三份文件记录流程、关键状态、反馈、错误恢复、验收方式、选稿版本与用户反馈；无 UI 影响则注明适用范围、理由和用户确认，可不出稿 |
| 4 | `docs/specs/<ID>.md` 项目方案（即执行用规格书） | 用[方案模板](TEMPLATE.md)合并已确认结论，引用输入版本；说明模块、数据和接口如何支撑目标、风险和 AC。记录合理性核对的结论、修正及待决定之处，关键矛盾未解不得拆实施清单 |
| 5–6 | `docs/plans/active/<ID>.md` 实施 Plan | 用[Plan 模板](../plans/TEMPLATE.md)把方案 AC 映射到可验证的编号项。第 5 步记录组合批准与实施授权状态（可未授权），第 6 步沿用同一份文件记录执行和验收 |

**每份产物开头是它自己的交接卡**：功能编号与范围｜本步、文档版本和状态（草案／待确认／已确认／需复核；跳过须注明依据）｜输入文件和版本｜用户确认了什么、依据是什么｜未决或阻塞｜当前写入者或已停写｜下一步由谁做什么。用已有字段即可；Plan 沿用顶部恢复入口。第一步两份记录分别反映访谈与调研状态。每次产生有效决定、中断或交接时更新，不等对话结束再凭记忆补写。文件缺失、草案和用户明确跳过是三件不同的事。

在[热路径](../paths.md)登记本功能当前入口；状态和授权以产物原文为准，不在索引复制审批台账。新会话结合提示词和文件判断：同一份报告可被另一个任务规划家只读复核；若输入已换版，先比对改动，只把受影响的下游结论标为需复核，再让相应角色和用户确认，不重做无关部分。修改上游决定的对话角色在自己的产物记新版本、旧版本和受影响范围；串行登记热入口指向这份变更，或交给当前索引写入者，在途者须收到停派／停写通知。有步骤已进入实施时，不越权改 Plan，也不把发出通知当作对方已停写。没有索引写权限，在回复中交接待同步项并明确哪些尚未通知。只读委托用相同字段在回复中交接，不宣称已保存。
