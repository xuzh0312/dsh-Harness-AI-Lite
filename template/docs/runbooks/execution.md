# 统筹执行家：执行与验收手册

本手册定义通用行为协议，无后台调度器或原生配置。入口为 [AGENTS.md](../../AGENTS.md)，角色职责见[角色协议](../../agents/README.md)，子 agent 使用限制见 [MODELS.md](../../agents/MODELS.md)。

## 1. 入口确认与任务记录

本手册从第 6 步开始。先按[入口](../../AGENTS.md#开始任务)定位本次范围；用户委托规划、设计或只读复核时，交回相应角色，不启动实施。

读取 Harness 入口、[路径表](../paths.md)及目标目录适用规则。确认三域实际位置、读取与写入权限、任务授权、当前代码状态及已有改动。路径未提供但能由当前工作区可靠确定时先检查；不使用的区域注明不适用，确有缺失且影响工作时再询问。

工作目录、规则加载与访问权限分别确认。Harness 是管理依据，执行目录按任务选择；业务命令通常在 project/code 执行，项目文档任务在 harness 执行。不可因工作区同时打开多个目录就认为它们共用仓库或权限。

功能计划使用 [PLAN 记录](../plans/TEMPLATE.md)。独立任务需审查、返工、跨仓库关联或跨会话交接时，按[编号与归档](../plans/README.md)建立 TASK 短交接。已有相关记录就续用，纯问答免建。未获记录写权限时在回复中交接，获准落盘后再分配正式编号。同一 Plan、文件或共享编号由一个会话串行维护；接手先确认原写入者已停写或已隔离。不同会话可负责无重叠的工作。

执行中每轮先看用户最新要求和纠正，再看当前项恢复入口中的范围和用户决定、有效授权、在途写入者、阻塞、下一步及证据位置。只补当前判断缺的材料：先按 PLAN、TASK、AC、BUG 编号或代码符号定位，未命中再按症状、模块扩大检索。旧对话、整段日志、无关任务和未采用的方案不默认载入；结论冲突时回到对应版本的原文与原始证据。

决策、假设、版本或在途状态改变时，替换恢复入口的当前状态，不逐轮追加摘要。保留用户批准和撤回依据、独立审查结论及原始证据引用。对话太长时先交接，再由接续会话核实真实文件、授权和在途状态；摘要不能清空已有对话，也不能代替授权。旧执行者失联不等于停写，未确认停写或隔离其写入范围前，只继续不重叠且已获授权的工作。

## 2. 定义验收并选择角色

明确目标、写入范围、预期行为和验证方式，按 ARCHITECTURE.md 核对文件归属。关键需求未决时先澄清；范围内的实现细节自行判断，只记录影响后续决策的取舍。

首版与新增功能必须有当前组合批准及实施授权。按[执行技能](../../skills/subagent-driven-execution/SKILL.md)串行派一个编号项；必要只读调查可并行。每个实现项由新执行者完成，两个只读审查者分别核对规格与质量，统筹执行家验收后再派下一项；当前批准范围的实现项均通过后，新建两个审查者做整体审查。依赖设计稿的项先按 test/README.md 恢复和校验固定版。出现新需求或验收变化，退回相应规划步骤，不在执行中改标准。

独立维护任务按实际影响处理，不以 TASK 名义实施未规划的新功能：

| 任务条件 | 分派与验收 |
| --- | --- |
| 纯问答、不改变规则含义的轻微文字调整 | 对话角色按授权直接答复或修改并核对 |
| 原契约下的缺陷修复，或脚本、构建等基础设施 | 明确原行为与基线 → 执行者修改 → 两个独立审查者 → 统筹执行家验收；没有功能方案时以原契约和本次要求为规格依据 |
| 首次启用或实际变更技术栈 | 按[选型与交接](../../skills/tech-stack-plan/SKILL.md#选型与交接)核对用户授权、完整候选差异与原栈；双审通过后原样写入并验收，再派依赖新栈的实现 |
| 影响后续决策的规则变更 | 统筹执行家或执行者修改 → 两个审查者独立演练 → 统筹执行家验收 |

只有非功能维护中的独立改动可在写入互斥且已授权时并行实现，整合后双审。强制审查缺任一维度即受阻，不以作者自审或单实例兼任替代。

## 3. 分派与整合

改动前确认必需角色能读取同一受审版本，运行器支持显式配置及独立上下文。需要看稿时先确认可恢复、可查看；遇到未决设计取舍时交回交互规划家与用户。缺少必需能力先说明阻塞。写入范围与用户未提交改动重叠时，先在获准位置保留可比对的改前内容与暂存边界，交接引用该基线；无法可靠区分时暂停重叠处的写入。分派按[交接模板](../../agents/TASK_TEMPLATE.md)给出路径、基线、范围、依赖与验收。

不超过运行器并发上限；容量不足时两个 reviewer 保留独立上下文顺序完成，并记录实际未并行；不能降为单 reviewer。其他任务容量不足时同样顺序执行。不并行写相同文件，不让子 agent 嵌套派生。统筹执行家也不在执行者工作期间修改其分配文件。关键设计决策尚未确认时，不启动依赖该决策的实现。任务涉及新技术栈时，按 [ARCHITECTURE.md](../../ARCHITECTURE.md) 核对生效依据后，再派发当前或后续依赖项。

等待期间有独立工作就先做；能接收完成通知时不反复查状态。收到回报后核对真实文件、范围与证据。实施中按有意义的进展简报已完成什么、下一步是什么。范围、已定行为或验收有实质变化，需要新增授权或遇到用户才能解除的阻塞时，再请用户决定。收尾说明结果、证据和未验证项。设计稿与原型只写指定的 test 位置，reviewer 对受审材料只读；发现越界改动先识别来源，不覆盖或撤销用户既有内容。

已批准功能计划的简报、执行者身份、派工前基线、交付及审查摘要、返工轮数与下一步集中在原计划，不另建进度台账。派工只传本项、必要接口、前置结果和全局约束，不复制整段聊天。原始差异、未提交内容的前置快照及验证产物放 test，harness 仅保留管理摘要和引用；未提交状态也必须覆盖完整任务差异，不能只看 HEAD~1。

## 4. 审查、返工与阻塞

按 [reviewer 协议](../../agents/reviewer/AGENT.md)向两个实例提供同一份要求、完整差异、执行报告和证据，冻结受审版本。分别保留实例身份、维度、轮次和结论；版本变化后两者都要复核，不能用一份通过抵消另一份问题。

同时提供 [bug-detect 技能](../../skills/bug-detect/SKILL.md)和 [项目错误知识库](../bugs.md)。reviewer 发现缺陷或复验时调用技能，返回查询和记录提议；统筹执行家写前重读最新知识库，按根因去重并串行分配编号或更新原条目。并行 reviewer 不直接写入。同类复发重新打开原记录，保留已验证方案的适用范围；没有新信息则不更新。

修复前核对旧方案是否适用，复核后满足关闭条件才记为已解决。用户要求只读时仅在对话中返回提议；获准写入但知识库不可写时再报告阻塞。审查和验证遵守任务授权，任务记录只引用已登记的 BUG ID。

统筹执行家按证据核实每项发现，不能降低验收标准；认为发现不成立时回传证据请 reviewer 复核，仍不一致按 reviewer 协议交用户裁决。返工优先恢复原执行者与本组 reviewer；无法恢复或配置已变时按当前配置交接。重验受影响部分，再按[双审核准条件](../../agents/reviewer/AGENT.md#发现与结论)决定能否验收。

多轮修同一缺陷时，恢复入口中的缺陷部分只记必须满足的行为、已证实的事实、已排除的假设及何时需要重查、仍未知的问题，以及下一项能区分假设的检查。证据引用对应版本，不抄修复流水。连续两轮无新证据就重查根因、方案和分派方式，不机械重试；确需用户决定时只问未决事项。

缺少必要权限、依赖、外部服务、关键需求或强制审查能力时记录具体阻塞、已尝试操作、影响和恢复条件。继续不依赖该条件的已授权工作；条件恢复后从记录位置续接，并核对已有证据是否仍有效。

## 5. 最终验收与状态

| 状态 | 进入条件 |
| --- | --- |
| 待处理 | 已有目标，尚未开始执行 |
| 待确认 | 功能规格与计划草案已生成或修订，等待用户确认当前组合；不得开始依赖实现 |
| 待实施授权 | 当前组合已批准，下一步需实施但尚未获准；保留在 active |
| 执行中 | 正在进行已授权的分析、设计或实现 |
| 验收中 | 交付可检查，正在审查或核对证据 |
| 返工 | 存在必须修复的发现，已分派处理 |
| 受阻 | 缺失外部条件或关键决策，阻塞部分有明确恢复条件 |
| 完成 | 目标范围、适用检查、强制审查和最终验收全部满足 |
| 已取消 | 用户取消任务，注明取消原因后归档，不代表已实现 |

状态由统筹执行家更新。只派获准项；实质修订回到待确认，返工修复后回到验收中。用户取消时停止相关派工，立即通知在途执行者停写，并停止本任务中仍会写入的命令。不能确认停写时报告受阻，不归档；确认后记录已发生的改动，不自行回滚。取消范围的实施授权终止，恢复须重新获准。

完成前逐项确认：

- 最终差异符合任务范围，用户既有改动得到保留；新增文件符合三域边界，未要求打包时没有生成安装包。
- 按 docs/paths.md 的收录范围核对根路径和稳定索引；未能核对的区域明确说明。
- 每项必需验收有证据，或具有合理的不适用说明；必需检查失败、未运行、关键证据缺失均不能标为通过。
- 证据写明工作目录、方法、结果和覆盖版本；仅重验受改动影响的部分。界面项按[最终验收模板](../plans/TEMPLATE.md)区分看稿、观察实际界面、操作和重开验证。
- 所有阻塞发现已修复并复核，或已按[结论冲突与用户裁决](../../agents/reviewer/AGENT.md#结论冲突与用户裁决)由用户裁定不阻塞；统筹执行家不自行裁定，不能将未满足的需求裁定为通过。
- 所有强制审查范围均有两个独立实例的报告，分别覆盖规格符合性和实现质量，对应同一最终版本，并按[双审核准条件](../../agents/reviewer/AGENT.md#发现与结论)核对原始结论及裁决；容量不足的顺序审查如实记录，不冒充并行。
- 若功能计划仍有未获实施授权的项，记录本次交付及恢复位置，保留在 active 等待实施授权。
- 已实施的功能计划按当前批准范围核对逐项验收、全功能规格覆盖、跨项集成、回归及整体双审；后续修改影响的条目已重新验收。
- 用户可理解交付结果、限制与剩余问题。审查通过不代表发布、合并或目标机器验收已发生。

已有记录时先填写结果，任务完成或取消后将 PLAN 或 TASK 移入 completed，PLAN 同步修正规格链接，最后按[热冷切换](../paths.md#热冷切换)核对仍被引用的证据与冷档。其余保留 active。归档保留历史批准，不恢复已撤回的授权。记录代码及数据版本；未提交时记明基线、已有改动边界与最终差异。原始证据留在 test，计划只存摘要与引用。

harness、project/code 与 test 分别版本控制。验收通过不自动授权提交、推送、合并、发布或破坏性操作；按当前任务明确授权执行，记录实际完成的交付阶段。
